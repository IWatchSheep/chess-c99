What 3B adds (spec v1.4, Section 7, "3B in detail")
1. After a preview, "replies" lists every legal reply of the other side:
     REPLIES BEGIN <m>
     THREAT <side> <moves> | THREAT <side> none
     NO REPLIES checkmate|stalemate   (only when m ends the game)
     REPLY <r> <label> White U1 U2 U3 GAINED RESTORED OPENED Black ...
     SUMMARY REPLIES n STOPS n LEAVES n NO-THREAT n ALLOWS n
     REPLIES END
   Labels concern the mover's mate-in-one moves only:
     STOPS (threat before, none after the reply), LEAVES (one remains),
     NO-THREAT (none before, none after), ALLOWS (none before, one after).
2. The counts on each REPLY line are exactly the COUNT lines of the 3A report
   of that reply from B' (after m), with m treated as finalized: a pair m
   took away that the reply gives back is RESTORED (E3: 3.Qh5 g6 shows Black
   GAINED 3 RESTORED 2).
3. "replies <move>" prints the full 3A report of one reply (B' -> B'').
4. Fixed order: start square, end square (rank 8 to 1, file a to h),
   promotion Q, R, B, N. Deterministic.
5. Nothing is chosen, scored or played; board, turn, history and the
   count-once memory are unchanged (tested). No weights, no Side A/B.

One decision for you to check
- When m itself ends the game (checkmate or stalemate) there is nothing to
  answer, so the view prints NO REPLIES and no THREAT line. Computing the
  mover's "mate in one" there would mean letting the mover move twice in a
  finished game, which lists meaningless moves (after Qxf7# it listed 24).
- Observation, not changed: the 3A report's MATE1 line (approved, fixed by
  golden_08) has the same effect after a move that ends the game, because
  MATE1 is defined as "the side's mate-in-one moves after the move" with the
  turn ignored. Should a later stage suppress MATE1 when the game is over, or
  keep the 3A definition as it is?

Windows fix found by the owner's test run
- On the owner's PC (Windows, MinGW GCC 15.2, CLion's CTest) the three test
  programs passed, but all 10 transcript tests failed, also the seven of
  version 5. The saved output stopped at the first prompt: the game received
  no input. Since version 1, main() runs system("chcp 65001 > nul") on
  Windows; the cmd.exe it starts used up the redirected input file before the
  game read it. The call now runs only when the input is a real console
  (_isatty(0), from <io.h>, inside #ifdef _WIN32). The game's output is pure
  ASCII, so the transcripts do not depend on the code page. Nothing changes
  on Linux; the golden files were not changed. The transcript tests had only
  been run on Linux before.
